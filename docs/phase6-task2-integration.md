## 3. 2-3 — 동시 수정 정책 결정 및 테스트

테스트: `backend/src/test/java/com/rea/academy/service/ConcurrencyPolicyTest.java` (4건)

### 3.1 정책 결정 (2026-10-13)

- **결정: 낙관적 락(`@Version`) 도입을 권장한다** (데이터 안전성 우선).
- **현재 상태: 미구현** — 수정 가능 엔티티 5종(`ReaStudent`·`ReaMember`·`ReaClass`·`ReaNotice`·`ReaAttendanceEvent`)에 `@Version` 없음 (리플렉션 테스트로 확인·고정).
- **현재 동작: 마지막 쓰기 승리(last-write-wins)** — 2개 세션/스레드가 같은 반을 수정해도 예외 없이 마지막 쓰기가 반영됨을 테스트로 기록.
- **코드 변경 없음**: 낙관적 락은 엔티티 스키마 변경(버전 컬럼)을 수반하므로 본 작업에서는 정책 결정 + 현재 동작 기록까지만 수행.

### 3.2 낙관적 락 도입 시 범위 (후속 승인용 보고)

1. 5개 엔티티에 `@Version Long version` 추가 (H2 `ddl-auto=create-drop`이라 스키마는 자동 반영, 운영 전환 시 Flyway 필요)
2. 동시 수정 충돌 시 `OptimisticLockException` → 프론트에 409 + "다른 사용자가 수정했습니다. 다시 확인하세요" 안내 필요
3. 부분 업데이트(null=no-change) 관행과 충돌 가능성 검토 (아래 3.3의 capacity 버그와 같은 맥락)
4. 영향 테스트: `ConcurrencyPolicyTest`의 last-write-wins 테스트 2건은 정책 변경 시 실패하도록 설계됨 (정책 드리프트 감지용)

### 3.3 관련 발견 — 학생 정보 수정 API 미구현 (중요)

- `MemberService.updateStudent()`는 `UpdateRequest` 값을 **엔티티에 반영하지 않는 no-op**이다
  ("실제 구현 시 setter 또는 update 메서드 사용" 주석만 존재).
- 학생 정보 수정용 `PUT /students/{studentId}` 엔드포인트가 **컨트롤러에 미등록**이다.
- 따라서 학생 정보의 HTTP 레벨 동시 수정은 현재 발생할 수 없으며, 본 테스트는 실제 값을 반영하는
  `ClassService.updateClass`를 대상으로 수행했다.
- **후속**: 학생 정보 수정이 필요해지면 API 구현 + 낙관적 락을 함께 적용할 것.

### 3.4 발견·수정 — 반 부분 업데이트 시 capacity 초기화 버그 (수정 완료)

- 현상: `PUT /classes/{id}` 로 이름만 수정하면 `capacity`(정원)가 **null로 조용히 초기화**됨.
- 원인: DTO는 "null이면 변경 없음"을 문서화하고, 서비스도 weekdays·시각은 기존값으로 보존하지만,
  `capacity`만 `req.getCapacity()`(null)를 그대로 전달 → `ReaClass.update`가 무조건 대입.
- 수정: `ClassService.updateClass`에서 `capacity`도 null이면 기존값 유지 + `ReaClass.update`에 null 가드 추가 (2곳, 각 1~2행).
- 검증: `ConcurrencyPolicyTest.partialUpdate_preservesUnspecifiedCapacity` PASS, 기존 `ClassServiceTest` 15/15 회귀 PASS.
- 의미: 동시·부분 수정 시 한쪽이 의도치 않게 다른 필드를 지우는 "조용한 데이터 손실" 유형. 낙관적 락 도입 시 함께 재점검 필요.

## 4. 2-4 — 장애 복구 시나리오 검증

### 4.1 트랜잭션 롤백 — PASS

테스트: `RecoveryTest.unexpectedFailure_rollsBackMultiWrite` (서비스 레벨)
- `REQUIRES_NEW` 트랜잭션 안에서 학생 등록 → 출결 기록 → **강제 RuntimeException** 발생
- 결과: 학생·출결 이벤트 **둘 다 DB에 남지 않음** (전체 롤백) ✅

정책 기록:
- CSV 일괄 가져오기(`importStudentsCsv`)는 **의도적으로 행 단위 부분 성공**을 허용한다
  (오류 행은 건너뛰고 정상 행은 반영, 오류 목록 반환). 전체 롤백이 아니므로 운영 안내 시 명시 필요.
- 출결 기록·정정은 **검증 실패 시 쓰기 전에 차단**되어 부분 데이터가 생기지 않는다
  (존재하지 않는 학생·정정 사유 누락 → `IllegalArgumentException`, 원본 무결성 유지).

### 4.2 세션 만료 — PASS

- 인증키 갱신(`POST /members/{id}/renew-key`, `POST /students/{id}/renew-key`) 후 **구 키 → 401**, 신 키 → 200 ✅ (`IsolationMatrixTest`)
- 프론트 동작 (코드 검증, `frontend/components/api-client.js`):
  - 401 → 저장된 인증키 삭제 + **MBR-07 로그인 화면으로 리다이렉트** ✅ (이미 로그인 화면이면 이동 생략으로 루프 방지)
  - 403 → `alert('권한이 없습니다')` ✅
- 학부모 화면(키 직접 입력)은 `keyOverride`로 전달한 키를 삭제하지 않음 ✅

### 4.3 네트워크 장애 시뮬레이션 — 코드 검증 + 발견 2건 (후속)

| 항목 | 상태 |
|---|---|
| API 타임아웃 설정 | **없음** — `fetch()`에 `AbortController`/timeout 미설정. 응답이 멈추면 무기한 대기 (브라우저 기본 동작) |
| 401/403 처리 | 중앙 처리됨 (상기) ✅ |
| 네트워크 단절 시 오류 표시 | **화면별 상이** — GRD-02·RPT-01·ADM-*·ATT-01/04·CHAT-01·HW-*는 try/catch로 오류 메시지 표시 (예: GRD-02 `showMsg('서버 연결 실패')`), **MBR-01·ATT-02 등은 try/catch 없이 unhandled rejection** → 목록이 비어 보이기만 하고 오류 안내 없음 |
