# REA 수납·결제 방침 (1페이지 요약)

> 작성일: 2026-10-13 (5단계 작업 5)
> 경계: 수납·결제 기능 개발 금지 (프로젝트 경계). EASY 장부는 READ ONLY (기존 데이터·회계 로직 변경 금지).

---

## 1. 방침: REA에서 수납·결제 미구현 유지 (의도적)

REA(학원관리)에는 **수납·결제 기능을 만들지 않는다.**
이는 기술적 미비가 아니라 의도적인 설계 결정이다. 이유:

1. **책임 분리**: REA는 학원 운영 관리(출결·공지·상담·숙제·성적) 시스템이다. 돈의 흐름(청구·수납·정산·회계)은 별개 도메인이다.
2. **검증된 외부 서비스 존재**: 비대면 결제는 결제선생(Payssam) API로 이미 해결 가능하다. 같은 기능을 REA 안에 다시 구현하는 것은 중복 투자다.
3. **회계 무결성**: 장부 집계는 EASY 기존 흐름이 담당한다. REA에 금액·수납 상태를 저장하기 시작하면 두 장부가 어긋나는 순간이 온다.

## 2. 결제선생 외부 연결 방침 (학원이 직접 계약)

- 비대면 결제는 **결제선생 API**를 활용한다. 인증 = API키 + 사업장코드 + SHA-256 해시.
- 구조: 플랫폼 1개 + 학원별 하위사업장. **학원이 결제선생과 직접 계약**한다 (플랫폼이 대행 계약하지 않음).
- 시작점: `POST /bill` 청구서 발송 (건당 55원). 직접 카드결제 API는 없고, 청구서 발송이 결제 흐름의 시작이다.
- REA 측 역할: **없음**. REA의 반·학생 데이터가 결제 근거로 필요하면 **읽기 전용 조회**까지만 허용하고, 금액·수납 상태는 절대 REA에 저장하지 않는다.
- 홈페이지의 결제 버튼은 결제선생 청구 링크로만 연결한다.

## 3. REA(LMS)에 수납·회계 DB가 없음 — 명시

- REA 데이터베이스에는 `수납·결제·회계` 관련 테이블·컬럼이 존재하지 않는다. 앞으로도 추가하지 않는다.
- 금지 목록: 수납 금액·미납 상태·청구서·정산·PG 수수료율·환불 — 전부 REA 저장 금지.
- 경계 위반 방지 체크리스트 (`docs/buildit-integration.md` §2): "결제·수납·회계 로직이 REA에 들어오지 않았는가?" — 신규 개발 시 매번 확인.

## 4. EASY 장부 (기존 운영 흐름 유지)

- 장부 집계는 **EASY 기존 흐름을 그대로** 둔다.
- EASY 장부 실데이터 작업 시 원칙: **READ ONLY**. 기존 데이터·회계 로직 변경 금지.
- REA와 EASY는 직접 연결하지 않는다. (결제 근거가 필요하면 REA 읽기 전용 조회 → 결제선생/EASY 측에서 처리)

---

*수납·결제 관련 변경은 사용자 별도 승인 없이는 설계·구현 모두 하지 않는다.*
