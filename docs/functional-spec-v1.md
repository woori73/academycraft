## 1. 학생·학부모·강사 관리

### 1.1 화면 목록

| 화면 ID | 화면명 | 사용자 | 설명 |
|---|---|---|---|
| MBR-01 | 학생 목록 | 원장·강사 | 등록된 학생 목록 조회·검색 |
| MBR-02 | 학생 등록 | 원장 | 학생 정보 입력 → 인증키 자동 발급 |
| MBR-03 | 학생 상세 | 원장·강사 | 학생 정보·인증키 확인, '보내기' (카카오톡/문자 공유) |
| MBR-04 | 강사 목록 | 원장 | 등록된 강사 목록 |
| MBR-05 | 강사 등록 | 원장 | 강사 정보 입력 → 강사 인증키 발급 |
| MBR-06 | 강사 상세 | 원장 | 강사 인증키 확인 (원장만) |
| MBR-07 | 로그인 | 학부모·강사·원장 | 인증키 입력 로그인 (회원가입 없음) |
| MBR-08 | 내 정보 | 전체 | 본인 역할·소속 학원·반 확인 |

### 1.2 화면별 상세

#### MBR-01 학생 목록
- UI 요소: 검색창(이름), 반 필터, 학생 카드 목록 (이름·반·최근 출결 상태)
- 기능: 학생 검색·반별 필터링, 학생 상세로 이동
- 데이터: 학생 ID, 이름, 소속 반, 인증키 발급 여부

#### MBR-02 학생 등록
- UI 요소: 이름 입력, 반 선택, [등록] 버튼
- 기능: 학생 생성 → 학생 인증키 자동 발급 (영문+숫자 조합)
- 데이터: 이름, 반 ID, 학원 ID (테넌트), 인증키
- 재사용: `Student` 엔티티 (parent_name/parent_phone 컬럼 활용)

#### MBR-03 학생 상세
- UI 요소: 학생 정보 표시, 인증키 표시, [보내기] 버튼 (카카오톡/문자 공유), [수정], [삭제]
- 기능: 인증키를 학부모에게 공유. 삭제 시 확인 절차 (데이터 복구 불가 안내)
- 데이터: 학생 전체 정보 + 인증키

#### MBR-04/05/06 강사 관리
- MBR-02/03과 동일 패턴. 강사 인증키는 원장 화면에서만 확인 가능.
- 재사용: `User` 엔티티 + `Role` enum (TUTOR)

#### MBR-07 로그인
- UI 요소: 인증키 입력창, [로그인] 버튼, 학원 선택 (필요 시)
- 기능: 인증키 검증 → 역할 판별 (원장/강사/학부모) → 해당 홈으로 이동
- 비투 방식: 전화번호 입력·회원가입 없음. 인증키만으로 로그인.
- 재사용: `AuthController` JWT 패턴 참조. 단, 인증키 방식은 신규 구현.

### 1.3 권한 체계

| 역할 | 인증 | 접근 범위 |
|---|---|---|
| 원장 (ACADEMY_OWNER) | 원장 인증키 | 전체 관리 |
| 강사 (TUTOR) | 강사 인증키 | 담당 반 학생 조회, 출결·소식·상담 |
| 학부모 (PARENT) | 학생 인증키 | 자녀 정보만 조회 |

- 재사용: `SecurityConfig` 역할 기반 접근 제어 패턴. `Role` enum에 PARENT·ACADEMY_OWNER 추가 (기존 값 변경 금지).

### 1.4 API (개념)

```
POST   /api/rea/{academyId}/students          # 학생 등록
GET    /api/rea/{academyId}/students          # 학생 목록
GET    /api/rea/{academyId}/students/{id}     # 학생 상세
PUT    /api/rea/{academyId}/students/{id}     # 학생 수정
DELETE /api/rea/{academyId}/students/{id}     # 학생 삭제
POST   /api/rea/{academyId}/teachers          # 강사 등록
GET    /api/rea/{academyId}/teachers          # 강사 목록
POST   /api/rea/auth/key-login                # 인증키 로그인
```

### 2.2 화면별 상세

#### CLS-01 반 목록
- UI 요소: 반 카드 목록 (반 이름·학생 수·담당 강사)

#### CLS-02 반 생성
- UI 요소: 반 이름 입력, 설명 입력, 담당 강사 선택, [생성] 버튼
- 데이터: 반 ID, 학원 ID, 반 이름, 담당 강사 ID

#### CLS-03 반 상세
- UI 요소: 소속 학생 목록, [학생 추가] (학생 목록에서 선택), [제외] 버튼
- 기능: 반-학생 매핑 관리. 반 소식·공지 발송 시 대상이 됨.
- 신규 개발: `LmsEnrollment`는 수업 상품 기준이므로 반-학생 매핑 테이블 신설 권장.

Class (반)

ClassEnrollment (반-학생 매핑)
- id, class_id (FK), student_id (FK), enrolled_at, is_active
```

### 2.4 API (개념)

```
POST   /api/rea/{academyId}/classes           # 반 생성

## 3. 출결

### 3.1 화면 목록

| 화면 ID | 화면명 | 사용자 | 설명 |
|---|---|---|---|
| ATT-01 | 출결 입력 (키패드) | 공용 단말 | 학생이 출석키 입력 |
| ATT-02 | 출결 현황 (월별) | 원장·강사 | 월별 출결 집계표 |
| ATT-03 | 출결 상세 | 원장·강사 | 학생별·일자별 출결 기록 |
| ATT-04 | 출결 설정 | 원장 | 하원 가능 시간·알림 문구·사진 전송 여부 |

### 3.2 화면별 상세

#### ATT-01 출결 입력 (키패드)
- UI 요소: 숫자 키패드, 학생 이름 표시 (입력 후), 등원/하원 자동 판별
- 기능: 학생이 출석키 입력 → 등원 또는 하원 기록 → 학부모에게 실시간 알림
- 비투 방식: 중고 스마트폰·태블릿에 출결앱 설치. 여러 대 동시 사용 가능.
- 신규 개발: 출결 관련 코드가 코드베이스에 전무.

#### ATT-02 출결 현황 (월별)
- UI 요소: 달력 형태, 일자별 출결 상태 색상 표시, 월 선택
- 기능: 월별 출결 집계 확인. PDF 저장·프린트 (PC).

#### ATT-03 출결 상세
- UI 요소: 학생별 출결 기록 목록 (등원 시각·하원 시각·상태)
- 데이터: 출결 이벤트 (학생 ID, 일시, 구분(등원/하원), 사진(선택))

#### ATT-04 출결 설정
- UI 요소: 하원 가능 시간 설정, 알림 문구 편집, 출결 사진 전송 ON/OFF
- 비투 확인 설정: 실시간 등·하원 알림, 하원 가능 시간, 알림 문구 변경, 출결 사진 전송

### 3.3 데이터 모델 (개념)

```
AttendanceEvent (출결 이벤트)
- id, academy_id (FK), student_id (FK), class_id (FK, nullable)
- event_type (CHECK_IN / CHECK_OUT)
- occurred_at, photo_key (nullable, FileStorage)
- created_at
```

### 3.4 API (개념)

```
POST   /api/rea/{academyId}/attendance/check   # 출결 기록 (키패드 입력)
GET    /api/rea/{academyId}/attendance/monthly # 월별 현황
GET    /api/rea/{academyId}/attendance/student/{studentId}  # 학생별 기록
PUT    /api/rea/{academyId}/attendance/settings  # 출결 설정
```

### 3.5 알림 연동
- 출결 이벤트 발생 → 알림 발송 (4. 알림 참조)
- 등원/하원 시 학부모 앱 푸시 + 선택적 사진 전송

## 4. 알림

### 4.1 화면 목록

| 화면 ID | 화면명 | 사용자 | 설명 |
|---|---|---|---|
| NTF-01 | 알림 목록 | 학부모·강사·원장 | 수신한 알림 목록 |
| NTF-02 | 알림 설정 | 학부모 | 알림 종류별 ON/OFF |
| NTF-03 | 발송 이력 (관리자) | 원장 | 알림 발송 성공·실패 이력 |

### 4.2 알림 종류

| 종류 | 트리거 | 수신자 |
|---|---|---|
| 등원 알림 | 출결 이벤트 (CHECK_IN) | 학부모 |
| 하원 알림 | 출결 이벤트 (CHECK_OUT) | 학부모 |
| 공지 알림 | 공지 등록 | 대상 학부모 |
| 상담 답변 알림 | 상담 답변 등록 | 문의 작성 학부모 |
| 성적·숙제 알림 | 성적·숙제 등록 | 학부모 |

### 4.3 발송 채널
- 1차: 앱 푸시 (FCM) — 비투는 앱 알림으로 문자 비용 0원
- 2차: 알림톡/SMS (외부 연동, 별도 계약 필요)
- 발송 이력 테이블: 수신자·채널·상태·재시도 횟수

### 4.4 신규 개발
- 코드베이스에 SMS/푸시/알림톡 발송 코드 없음. 외부 서비스 연동 필요.
- `students.parent_phone`을 수신자 연락처로 활용.

## 5. 공지

### 5.1 화면 목록

| 화면 ID | 화면명 | 사용자 | 설명 |
|---|---|---|---|
| NTC-01 | 전체공지 목록 | 학부모·강사·원장 | 학원 전체 공지 목록 |
| NTC-02 | 반소식 목록 | 학부모·강사·원장 | 소속 반 소식 목록 |
| NTC-03 | 공지 작성 | 원장·강사 | 전체공지 또는 반소식 작성 |
| NTC-04 | 공지 상세 | 전체 | 공지 내용·첨부파일·조회수(관리자만) |

### 5.2 화면별 상세

#### NTC-03 공지 작성
- UI 요소: 대상 선택 (전체공지/반 선택), 제목·내용 입력, 파일 첨부 (사진·영상·음성·문서), [발송] 버튼

- 재사용: 수업 커뮤니티 `LessonCommunityPostType.NOTICE` 또는 패턴 복사. `FileStorage`로 첨부파일 저장.

#### NTC-04 공지 상세
- 조회수는 관리자(원장·강사)에게만 표시 (비투 확인 사항)

### 5.3 데이터 모델 (개념)

- id, academy_id (FK), class_id (FK, nullable — null이면 전체공지)
- title, content, author_id (FK)
- created_at, view_count
```

### 5.4 API (개념)

```

## 6. 상담

### 6.1 화면 목록

| 화면 ID | 화면명 | 사용자 | 설명 |
|---|---|---|---|
| CNS-01 | 문의 목록 | 학부모 | 본인 문의 목록 |
| CNS-02 | 문의 작성 | 학부모 | 1:1 문의 작성 (텍스트·사진) |
| CNS-03 | 문의 모음 | 원장·강사 | 학부모 문의 모아보기·답변 |
| CNS-04 | 아이소식 | 강사→학부모 | 개별 학생 소식 1:1 전달 |
| CNS-05 | 대화 상세 | 전체 | 1:1 대화 스레드 |

### 6.2 화면별 상세

#### CNS-02 문의 작성 (학부모)
- UI 요소: 제목·내용 입력, 사진 첨부, [전송] 버튼
- 기능: 1:1 문의 등록 → 원장·강사에게 알림

#### CNS-03 문의 모음 (원장·강사)
- UI 요소: 미답변/답변완료 필터, 문의 목록, 답변 입력
- 기능: 문의 확인·답변 작성 → 학부모에게 알림

#### CNS-04 아이소식 (강사→학부모 1:1)
- 비투 핵심: 진도 상황·개별 영상·작품 사진·성적표 등 민감정보를 특정 학부모에게만 1:1 전달
- 부모도 글쓰기 가능 (양방향)

### 6.3 데이터 모델 (개념)

```
Consultation (상담 스레드)
- id, academy_id (FK), student_id (FK)
- type (INQUIRY: 학부모→학원 / NEWS: 학원→학부모 1:1)
- status (OPEN / ANSWERED / CLOSED)
- created_at

ConsultationMessage (상담 메시지)
- id, consultation_id (FK), sender_id (FK), content
- attachment_key (nullable), created_at, is_read
```

### 6.4 재사용
- 수업 커뮤니티 `QNA` 패턴 참조. `lessonId` 기준이므로 반/학생 기준으로 변형 시 별도 도메인 신설 검토.

## 7. 성적·숙제 관리

### 7.1 화면 목록

## 화면-기능 분리 설계

### 아키텍처 원칙
```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  UI Layer   │────▶│ Service Layer│────▶│ Domain Layer│
│ (교체 가능)  │     │ (업무 로직)   │     │ (엔티티)     │
└─────────────┘     └──────────────┘     └─────────────┘
     │                     │                    │
     ▼                     ▼                    ▼
 BuildIt 전용 UI      변경 없이 재사용      변경 없이 재사용
 로 교체 가능
```

### 분리 규칙
1. **Domain Layer**: 순수 업무 엔티티·값 객체. UI 의존성 없음.
2. **Service Layer**: 업무 로직·트랜잭션. DTO로 입출력. UI 프레임워크 의존 없음.
3. **UI Layer**: 화면 렌더링만 담당. Service Layer의 DTO를 받아 표시.
4. UI 교체 시 Service·Domain은 그대로 두고 UI Layer만 교체한다.

### 1차 구현 범위
- Domain + Service Layer를 먼저 구현 (업무 기능 확보가 목표)
- UI는 최소 기능의 심플한 화면으로 구현 (디자인 차별화는 2차)
- API는 RESTful로 설계하여 향후 BuildIt UI·모바일 앱에서 재사용 가능
