## 3. BuildIt 홈페이지 연동 가능 범위

(상세 실측 근거: `docs/phase6-task3-buildit.md`)

### 3.1 가능한 것

| 항목 | 내용 |
|---|---|
| 홈페이지 → REA 학원관리 이동 링크 | **가능 (편집기 코드 변경 불필요)**. 홈페이지 편집기는 콘텐츠(버튼/링크) 편집 기능이므로, 학원 운영자가 REA URL을 링크로 다는 것은 콘텐츠 편집이지 코드 변경이 아님 |
| 학원 식별자 매핑 | 가능. 서브도메인 handle → 서버사이드 `academy_id` resolve → REA URL의 `{academyId}`에 주입 (handle ↔ academy_id ↔ REA academyId 동일값 사용이 전제) |
| REA 독립 배포 | 가능. wemade-reorg 코드 import 0건 (`grep "import f2r"` 0건), 독립 패키지 `com.rea.academy`, 별도 인증 체계. URL + 식별자 값의 약속만 공유 |

### 3.2 조건부 가능한 것

| 항목 | 조건 |
|---|---|
| 홈페이지 상담 신청 → REA 상담관리 데이터 연결 | **조건부 가능**. 핵심 실측: 홈페이지에 **실제 상담 신청 폼이 없음** (연락처 채널 모달만 존재 — tel/mailto/카카오 링크). 연결하려면 아래 승인 항목 중 택1 필요 |

### 3.3 불가능한 것

| 항목 | 이유 |
|---|---|
| 익명 방문자의 REA 상담 API 직접 호출 | `POST /consultations`는 X-Auth-Key 필수(익명→401) + 등록 학생 필수. 방문자(프로스펙트) 개념이 REA에 없음 |
| 편집기 코드 무수정으로 홈페이지 서버가 폼 데이터를 REA로 자동 전송 | 홈페이지 서버/편집기 코드 변경이 필요한 영역 (본 작업의 "편집기 변경 금지" 조건 하에서 불가) |

### 3.4 필요한 승인 항목

1. **방문자 상담 접수 방식 선택 (택1)**: ① REA 측 공개 접수 API + 공개 폼 페이지 신설 (예: `POST /api/rea/{academyId}/inquiries/public`, 인증 체계와 별도 경로, rate limit + 일일 접수 상한 + 개인정보 역할 제한) 또는 ② 홈페이지 측 상담 신청 폼 신설 (편집기/서버 코드 변경 필요 — 별도 승인 사항)
2. **①번 선택 시 REA 소규모 개발 승인**: 공개 접수 API 1개 + 공개 폼 페이지 1개 + 관리자 접수 조회 ("대규모 기능 추가"는 아님)
3. **REA 배포 URL·도메인 확정** — 이동 링크 설정의 전제조건
4. **`academy_id` = REA `academyId` 일치 고정** — 프로비저닝 시 확정

#### 6.2 시범 운영 전에 반드시 해결할 항목

1. **#2 — 학생 수정 API 구현** (`PUT /students/{studentId}` + 서비스 실제 반영). 예상 2~3일, 신규 API이므로 승인 필요.
2. **#4 — MockNotificationSender PII 로그 마스킹**. 예상 반나절, 승인 불필요.
3. **#6 — 비활성 학생 이력 조회 정책 결정** (허용 시 관리자 전용 조회 정책 문서화). 승인 필요 (운영 정책).

#### 6.3 시범 운영 개시 후 조건·순서 권장

1. #3 테스트 격리 이슈 해결 → CI 구성 (build + test, 브라우저 E2E 반복 실행 금지).
2. #1 월별 출결 N+1 최적화 (사용량 증가 전).
3. #5 fetch 타임아웃·공통 오류 표시, #7 낙관적 락 도입 (운영 피드백 반영).
4. #8 BuildIt 상담 연결 — §3.4 승인 항목 결정 후 진행. 그 전까지는 REA 독립 URL + 홈페이지 이동 링크 방식으로 운영.
5. MySQL 전환·Flyway V1 적용은 **별도 승인** 후 진행 (현재 DDL·프로파일은 초안).

#### 6.4 본 판정의 한계

- H2 인메모리 기준 검증. 운영 MySQL·네트워크 환경에서는 응답시간·동시성 재측정 필요.
